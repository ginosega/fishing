## 2. Atomicity review of P3-31/P3-32

**Blocking finding:** P3-31 operator verifier currently consumes an approval in a separate step. P3-32 ledger makes that one use durable, but a crash before command acceptance strands the approval; the existing P3 internal command gate also consumes its HMAC nonce separately. The old scripts cannot simply be composed as-is and activated.

Cloudflare documents `D1Database.batch()` as a transaction: all statements commit sequentially or a failure rolls back the entire group. https://developers.cloudflare.com/d1/worker-api/d1-database/ . In this design, the signed approval, command-HMAC nonce, operation, canonical snapshot and existing trigger-inserted Accepted audit are all written **in one D1 batch**. Any reused approval UUID/digest, reused HMAC nonce, duplicate owner/repository/idempotency key or invalid snapshot causes rollback of **all** writes, including trigger audit. No `ON CONFLICT DO NOTHING` is allowed on these critical writes.

New source-only files:
- `design/p3_atomic_approval_acceptance.schema.sql`: unapplied proposed `p3_atomic_approvals` ledger with one-to-one FK to `p3_operations`, unique approval ID/digest, exact owner/repository, workflow/run, request hash/idempotency, issued/expiry/consumed timestamps. Not in active `migrations/`. Supersedes the separated `design/p3_operator_approval_ledger.schema.sql` for any future acceptance-enabled design. **Do not apply both ledgers as competing authorities.**
- `src/p3-atomic-acceptance-proof.mjs`: isolated, **not deployed** source-only composition. Runs fail-closed behind literal false-by-default flags and an injected trusted authorization verifier. The verifier must prove the GitHub OIDC/App identity, detached owner ECDSA signature, exact signed raw command-body hash and HMAC authenticity. The current local test adapter intentionally **mocks** that verification and is **not a deployable authentication implementation**. ## 3. Recovery and security boundaries not yet proved

- **Verifier integration**: P3-31 `createP3OperatorApproval` currently validates and consumes together, so it needs a separately reviewed **verify-only** interface. P3-20 `createP3InternalCommandGate` currently validates HMAC and consumes nonce separately, so it needs a corresponding pure cryptographic verification-only path. Neither may preconsume a credential when the atomic receiver runs. The future real isolated receiver must independently enforce verified OIDC/App/owner approval and HMAC on exact command bytes, not trust a client-provided `verified:true` object.
- **Trusted runner identity**: GitHub-signed OIDC token, workflow SHA and App GET installation identity require real private read-only proof. A Cloudflare Access service token authenticates the CI service, not the human owner. HMAC and origin alone do not prove signed owner approval.
- **Uncertain outcome**: an acknowledgment lost after a successful batch is still `UNKNOWN` at the client. No automatic reissue of approval, new nonce, new run or fresh idempotency key is allowed. An explicitly authorized read-only status lookup by the exact signed approval digest links to the same immutable operation. `Unknown` or absent row does not imply permission to retry. The existing operation state machine governs later Checking/merge/deploy verification, which is wholly separate.
- **Real schema/provider approval**: to move forward, review new schema as a NEW R5-like isolated migration (do NOT modify or rerun R1–R4), verify sandbox D1 identity, free-plan limits, FK/trigger, and a rollback/recovery plan. No real DB mutation, workflow installation, credentials or Worker enablement is authorized here. The P3-32 separated ledger is retained as historical source proof only and must NOT be deployed alongside the atomic design without an explicit migration reconciliation.
- **Publishing**: even an atomically Accepted sandbox command would not authorize GitHub PR creation, merge, production deploy or v3 cutover; all remain independent owner gates.
