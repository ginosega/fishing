## Implemented

1. [`src/sandbox-write-token.mjs`](src/sandbox-write-token.mjs): server-only, **deny-by-default** restricted GitHub App installation-token issuer. Requires both a trusted `enabled()` gate and exact `P3_WRITE_ENABLED=true`, and never accepts any repo other than **ID 1430581407**. Before token issuance, JWT-authenticated GitHub GET preflights verify the expected App ID, installation ID, GitHub owner `ginosega`, selected-only installation, unsuspended status, granted Contents R/W and Pull Requests R/W, and the same App installed on the expected sandbox. Requests a new limited installation token with **repository_ids: [1430581407], permissions: {contents: 'write', pull_requests: 'write'}** and fails unless the response confirms one exact repo and those exact two rights. Returns token only to trusted server code. **No token was issued using real credentials during this phase.**
2. [`src/sandbox-github-pr.mjs`](src/sandbox-github-pr.mjs): unconnected server-only draft PR adapter. The actual outbound GitHub API sequence is repo identity GET → current `main` exact SHA → deterministic `p3-test-<operation-id>` branch lookup → trusted Node-side candidate callback tied to exact `main` → read base Git commit → create text-only content-addressed blobs, Git tree, commit → re-read `main` SHA to reject mid-flight changes → **create new branch without force** → open **draft PR**. It supports **Gear/KB text only**; rejects media, deletes, workflow paths, traversal, duplicate paths, oversized content, wrong domain/identifier, mismatched repo ID, unvalidated candidates or stale `main`. It has **no merge, branch deletion, force-push, production fallback, hosted release or live publication method**.
3. Crash/retry guard: if the deterministic branch exists, the adapter requires an exact **server-owned durable receipt** (operation ID, expected base/head SHA, sandbox repo ID), checks the existing Git commit's single parent and verifies the unique PR's sandbox head identity. If a branch exists without that exact durable receipt, it returns `BRANCH_RECONCILIATION_REQUIRED` rather than adopting, overwriting, or duplicating the PR. **A future transaction/recovery integration must persist the receipt after GitHub side effects; until then an interrupted attempt may need manual reconciliation.**
4. [`test/sandbox-github-pr.test.mjs`](test/sandbox-github-pr.test.mjs) exercises the complete simulated GitHub HTTP call order, narrow repo scope, draft-only PR, deterministic retry, existing detached branch, forged/faulty PR identity, wrong main SHA, changed main during blob creation, invalid paths/domain, invalid token, disabled writes and wrong repo configuration.
5. [`test/sandbox-write-token.test.mjs`](test/sandbox-write-token.test.mjs) uses throwaway RSA keys and mocked GitHub responses to check token scope, user agent, API owner/sandbox identity, permission/installation mismatch, extra repo grants, and strict `P3_WRITE_ENABLED=false` denial.

## Remaining gates — not yet satisfied

- **No live write endpoint:** Neither new module is imported by the deployed P3 Worker. Worker remains write-disabled and temporary diagnostic key was deleted per owner. No source/DB migration or new GitHub workflow has been deployed.
- **Trusted validated candidate:** The adapter calls a `trustedCandidate` dependency, but this is not yet wired to a Node validator executed on an independently fetched, immutable sandbox `main` checkout. The sandbox contains only README, not a complete canonical PWA source. A browser/client-provided `validated:true` flag is NEVER acceptable. Need canonical snapshot acquisition, full schema/Markdown/media inventory and SHA-bound CI before first sample PR.
- **Trusted dispatcher:** Owner session issuance/cookie transport, CSRF, server-owned operation persistence `0002`, D1 CAS lease and GitHub side-effect reconciliation are not integrated into one backend. No write operation may be exposed until joined and adversarially tested.
- **GitHub policy/CI:** Sandbox `main` is currently **unprotected**. Do not auto-merge. Effective branch rules/required exact-head checks must be configured and verified for the owner's GitHub plan. GitHub's [List check runs for a Git reference](https://docs.github.com/en/rest/checks/runs#list-check-runs-for-a-git-reference) **requires Checks: read** on a private repository for GitHub App installation tokens. The publishing App does not currently have this permission. Before relying on the exact-head Checks API, request only **Checks: read** through a separate owner-approved App permission change (not Checks write or Actions write). Workflow-run API permissions are separate. No new rights were requested or granted in this phase. Do not change the App's permissions implicitly.
- **Hosted verification:** Empty sandbox has no production-like workflow/release identity. No tested branch/PR/merge-to-hosted-release linkage exists. Merged is never Live by assumption.
- **Credentials/approval:** Existing App private key stays only in Cloudflare secret storage and must never be exported here or into source. No paid plan, production repo installation, auto-merge, test-hosting or production cutover is approved by this work.

**Disposition:** The source-only GitHub draft-PR and restricted token components are implemented and unit tested. **P3 overall is not finished; the first live sandbox write/PR has NOT occurred.** Next appropriate source work is to integrate a genuinely trusted exact-head validation/dispatch contract, add durable side-effect receipts and recovery tests, and design/enforce the sandbox CI/branch-policy checks before a controlled live test.
