## 3. Hard blocker: App PEM custody vs a no-write, combined LIVE proof

**Do not place the existing write-capable GitHub App PEM into a new GitHub Actions job on the assumption that the job's `contents: read` limits it.** This would cross a consequential credential-custody boundary. The P3-39 code uses no App private key until a future separately approved trusted caller supplies it. No runnable secret-bearing private workflow has been added. Existing credentials are not requested from the user and must never appear in chat, GitHub source, Actions logs, job outputs or artifacts.

Two future approaches merit review:

**Preferred boundary:** keep the existing App private key in a narrowly isolated private server-side signer or verifier (potentially using existing private secret custody), with a **distinct authenticated and service-bound read-only challenge** from the GitHub runner. Require that service to verify the real signed OIDC token and its exact audience/owner/repo/run/workflow claims before signing an ephemeral App JWT or performing its own **GET-only metadata verification**. Return only fixed pass/deny; *never* return the App JWT or raw PEM. This approach requires separate threat-modeling, secret presence inventory, public endpoint/service-binding isolation review and an approved infrastructure change; no such service is deployed now.

**Alternative with explicit high-risk approval only:** inject the existing App PEM into an entirely isolated, manual-only owner-run GitHub Actions job as a secret, and restrict source to the exact verified, pinned GET-only composition. This still exposes write-capable App signing authority to that runner's trust domain; a malicious alteration or compromised runner could bypass the intended two GETs. It is not made harmless by a disabled publishing flag or `permissions: contents:read`, and was **not** authorized or executed in P3-39.

A simpler strategy is to treat the **separate established live OIDC and historical owner-run App read proofs** plus the newly tested local composition as sufficient for the **design milestone**, deferring a risky live combined proof until actual publishing activation requires it. That avoids credential movement merely to repeat evidence.
