## Completed source-only implementation

1. [`migrations/0002_durable_snapshot_and_audit.sql`](migrations/0002_durable_snapshot_and_audit.sql) extends the owner's already-created **isolated P3 D1** `0001` schema with a bounded `p3_requests` payload table and SQLite triggers that atomically audit Accepted/transition events and reject invalid state jumps. This migration has **NOT** been applied to Cloudflare. Don't reapply the already-manually-initialized 0001 schema. No additional Cloudflare account work is needed now.
2. [`src/d1-operation-store.mjs`](src/d1-operation-store.mjs) implements **idempotent atomic text-only acceptance**, operation/snapshot hash checks, stable repository-ID and configured owner-ID isolation, compare-and-swap worker claims, bounded leases with expiry recovery, guarded state advancement, event history and validated PR/merge/hosted-evidence field shapes. D1 `batch` atomically commits the Accepted operation + snapshot; SQLite triggers persist audit events within that transaction. Stored snapshots can be read after service restart; a competing Worker cannot advance another Worker's unexpired lease.
3. [`src/p3-owner-session-guard.mjs`](src/p3-owner-session-guard.mjs) implements a **strict read-only, server-owned D1 session authorization check** for *future* write endpoints, based on a first-party `__Host-fish_p3_session` cookie, bound CSRF header, exact HTTPS Origin, `Sec-Fetch-Site: same-origin`, POST, explicit publish intent, application/json and a fixed seven-day nonrenewing expiry. The numeric owner ID is supplied by trusted server configuration, never from the request. Expired, revoked, malformed or mismatched sessions fail closed. The guard **does not issue sessions or create cookies**; the approved trusted OAuth callback/session integration remains an independent prerequisite.
4. [`test/d1-fixture.mjs`](test/d1-fixture.mjs), [`test/d1-durability.test.mjs`](test/d1-durability.test.mjs), [`test/d1-transitions.test.mjs`](test/d1-transitions.test.mjs) and [`test/p3-owner-session-guard.test.mjs`](test/p3-owner-session-guard.test.mjs) use actual in-memory **SQLite** transactions/triggers (Node 24 `node:sqlite`), with a D1-shaped prepared-query facade. The tests cover atomic rollback, no duplicate acceptance/event, conflicting snapshots, restart/lease recovery, stale claims, lifecycle audit, illegal transitions, missing evidence, payload corruption, wrong owner/repo, oversized/unsupported media, and session/Origin/CSRF denials.

## Hard stop conditions and current limitations

- The P3 public Worker **still has no `POST /publications` route** and no authenticated write capability. The D1 store and session guard are not imported into the deployed Worker.
- The D1 snapshot adapter is **text-only and bounded to 128 KiB**. It accepts only a minimal Gear/KB package envelope and *deliberately rejects media*. It **does not perform full canonical source-aware validation**, conflict detection or image/Markdown inventory checks. Never interpret `accept` as a validated/publishable submission. The earlier Node `source-aware.mjs` candidate adapter must be integrated in a trusted Node validation job bound to an exact GitHub SHA before a real PR.
- The state store permits a `Live` transition only with **well-formed evidence fields**; it does not independently verify hosted release identity. The future job must verify actual CI, merge SHA and hosted release before calling `advance(...'Live')`. A failure after a GitHub side effect still needs deterministic external reconciliation before retrying.
- Session issuance from the trusted OAuth sign-in flow, exact owner numeric ID, cookie path/site mechanics, CSRF token issuance, live revocation, per-request rate limits, audit retention and all privilege tests are still necessary.
- **Sandbox branch protections:** The actual private `ginosega/fishing-p3-sandbox` has `main` unprotected. GitHub's [repository rulesets documentation](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository) lists private-repository enforced rulesets as available with GitHub Pro/Team/Enterprise, not GitHub Free. The owner's GitHub plan has **not** been checked; do not assume branch-rule enforcement is available on this private sandbox or pay/convert visibility without owner authorization. **No GitHub App bot merge can be enabled until effective, verified policy exists and the owner specifically approves the first real test merge.**
- GitHub App still installed **only in sandbox per owner settings**; do not add the production `ginosega/fishing` repository. No application, production or infrastructure cutover authority is implied.
