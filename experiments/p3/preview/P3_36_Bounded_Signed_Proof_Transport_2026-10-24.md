## New source-only components

### `src/p3-proof-envelope.mjs`: canonical versioned proof envelope

The proposed outer transport carries exactly seven signed-proof fields plus a fixed `v:1`: `bodyB64` (base64url of the **exact inner command bytes**), `oidcJwt` (signed GitHub runner assertion), `approval` (canonical 11-field owner-approved envelope), `operatorSignature` (ECDSA P-256), `hmacSignature` (SHA-256 HMAC over exact inner body, fixed internal method/path, nonce and timestamp), `nonceValue`, and `timestampMs`. Payload is **not** an Access JWT or Cloudflare service-token client secret. Signed GitHub/OIDC identity, human ECDSA and HMAC are all verified later at the private receiver and not trusted because they are present in the envelope.

Wire format: UTF-8, exact compact JSON with a fixed top-level field order, canonical signed approval field order and the exact raw JSON source used for the inner command (after reversible base64url encoding). The parser reserializes and **requires byte-for-byte equality** with the received outer JSON: duplicate keys at any outer/inner approval nesting depth, unexpected fields, whitespace variants, noncanonical escaping/base64, BOM/invalid UTF-8 and normalized inner JSON ambiguities are refused. The inner JSON must be exactly reproducible through `JSON.stringify` of the decoded command, so duplicate keys in nested content also cannot be silently resolved. This new rule is deliberately stricter than the legacy command schema and requires future runner-to-source validation.

Independent limits are **8,192 UTF-8 bytes** for the inner command, **10,000 characters** for the three-segment OIDC JWT, and **24,576 UTF-8 bytes** for the entire outer proof. Detached signatures and nonce/time fields have exact shape/length validation. The request reader enforces Content-Type, any declared Content-Length, a counted bounded stream and fatal UTF-8 decode; it cancels a rejected stream and never accumulates unbounded bytes. These limits must be re-reviewed using actual assertion sizes and full provider traffic before activation; they were not chosen to support images, Catch media or production uploads.

### `src/p3-proof-transport.mjs`: three separately disabled stages

1. `createP3ProofSender`: source-only runner-facing constructor. Builds a fixed-target `POST /p3/internal/accept` carrying the signed-proof envelope. The **injected** transport, not this module, must separately handle Cloudflare Access service-token authentication; the sender does not fabricate an Access JWT or use global fetch. Literal enable controls and an injected operator-approved callback must all pass before any request. **No automatic retry**. A response may only confirm `Accepted`, never `Live`.
2. `createP3ProofIngress`: proposed Access-facing ingress; independently checks exact HTTPS configured origin/path/method and a verified, pinned Cloudflare Access service-token JWT identity from an injected verifier before reading and forwarding the bounded canonical proof. Builds a Request for the same exact legacy internal logical signed path `/_p3/internal/command` and calls **only injected private `P3_COMMAND_SERVICE.fetch`**. The internal Request forwards only `Content-Type: application/json` and the byte-identical canonical outer proof payload. It **drops the incoming** `Cf-Access-Jwt-Assertion`, Access Client ID/secret, cookies, Authorization and all arbitrary headers, keeping distinct Cloudflare and GitHub credentials separate. No public/hosted fetch fallback is defined.
3. `createP3ProofPrivateReceiver`: private service-binding endpoint that parses the same canonical proof again, then calls an **injected** P3-33 atomic acceptance service, which must itself be constructed with the P3-34 **verify-only** cryptographic adapter and D1 batch implementation. The receiver does not treat a client-provided `verified:true` property as a credential; the v1 wire protocol prohibits such extra properties. It returns only narrow `Accepted` receipt, or redacted errors. The receiver has separate exact literal disabled flags and no D1 fallback. No source is imported by any deployed static-503 Worker.

**All three constructors remain experimental source factories, not live Worker entrypoints.** The private receiver's injected service can be replaced in local unit fixtures, but a future deployed composition must pin the reviewed production verifier, private secret and D1 binding and refuse arbitrary caller-supplied service implementations.
