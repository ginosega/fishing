## 1. Disposition

**No unreconciled requirement-level contradiction remains in the revised D1 *design*** after explicitly reconciling two original differences. **This is not an assertion that V3 implementation meets the requirements:** significant required D2–D6 features and several runtime integration/security proofs are still outstanding. The product acceptance matrix is not passed by mock tests or this audit.

1. **Real design conflict — extra human signature per Save:** P3-40/41's *mandatory* per-change ECDSA/independent attestor would violate signed-off **V3-SAVE-05** and approved UX Section 1/3/7 (one Save and Publish, no confirmation/approval ceremony). **Resolution in D1:** do NOT port these experiments to the normal authoring flow. The owner remains authenticated once via GitHub; every write is independently authorized server-side with session/CSRF, trusted App permissions, validation, status and audit. The older P3 research remains unmerged and inert.
2. **Real rollout-plan conflict — dedicated hosted preview:** The original implementation plan P3/P4/P8 and design Section 11.2 prescribe isolated preview acceptance and protected production v2. The owner has **explicitly superseded the separate-website portion**, consenting to direct development in the intended production hosting environment, including downtime. **Resolution in revised D1 and D1–D6 plan:** one production Cloudflare hosting environment, sandbox **repository/data** separation for early writes, test-only path at same production origin, no duplicate preview site, exact hosted test-byte verification, recoverable V2 and separately authorized final product/public-main cutover. This is a **user-authorized deployment-method variance**, not a unilateral alteration of the signed-off user experience or data safety.

**Three important integration safeguards remain OPEN, not “solved”:** incompatible P1/P3 session formats require reimplementation and tests; actual Cloudflare gateway/Pages bytes and PWA service-worker path/origin migration require end-to-end proof; production-first use cannot risk canonical data or claim sandbox content is public Live. The original signed-off user requirements do not have a waiver for these safeguards.

## 3. Specific D1 implementation pitfalls flagged by this audit

**A. Two incompatible session systems — do not plug P3 guard into AUTH worker unmodified.** The isolated AUTH-P0 Worker uses `__Host-fish_p0_session`, base64url SHA-256 session hash and a D1 `sessions` table, while the P3 owner guard assumes `__Host-fish_p3_session`, hex digest of cookie and CSRF, and `p3_sessions`. A direct reuse would reject legitimate sessions or create two independent identities. Choose one canonical cookie/token hashing/DB lifecycle; bind an authenticated anti-CSRF token, make all write decisions from the server-side owner numeric ID, and keep signout/revoke-all truthful.

**B. Backend and app on one production origin — service worker must not break authorization.** The signed design conditionally accepted this same-origin architecture after Android/Windows G1 feasibility. It is not automatically a finished V3 PWA. Ensure the service worker never serves cached `/api/v3/`, `/session`, `/auth` or private status responses; the immutable Pages proxy strips cookies/Authorization to upstream. Owner session and CSRF must survive installed-PWA navigation, while Work Offline may not trigger secret-bearing network requests. Reassess installed origin/scope/migration with user acceptance.

**C. Production-first approval doesn't mean canonical-test-data permission.** The site may be temporarily offline, but data preservation still applies. First test writes target the existing private sandbox repo ID `1430581407`, never public canonical repo `1350909744`. A published test path under the real Cloudflare gateway must have independent byte-identity proof and must not pollute or impersonate canonical content. If no safe isolated test path/hosted proof is feasible, stop and identify the obstacle; do NOT claim that successful private GitHub Actions CI is a hosted publication.

**D. GitHub App grant and branch protection review.** Production main's [ruleset #25742040](https://github.com/ginosega/fishing/rules/25742040) was read: default branch requires PR, strict `fishing-merge-ready` check from Actions App ID 15368, zero normal required reviewers, no bypass. This supports conditional auto-merge **only after true current-head/current-base GitHub confirmation**. Current dedicated sandbox App installation grants are historical owner evidence, not freshly retrieved; neither these privileges nor an App's signing key should silently be presumed present in the gateway. GitHub connector access to current installation metadata or some branch protection endpoints was restricted. No bypass.

**E. Cloudflare Free and automated status.** D1 chooses a single server-side trusted runtime and durable D1 leases; real CPU/subrequest/Cron quotas, secret binding and exact-worker deployment remain unverified. A 202 Accepted is a durable beginning, not success. Hosted verification must observe actual source/build/merge/release identity, not just a GitHub success status.

**F. Feature completion and source PR hygiene.** D1 was a design milestone; it did not implement the V3 owner UI, Catch editor, integrated uploads, persistent Offline toggle or Markdown image viewer. Do not merge public draft P1/P3 experiments wholesale into `main`: port reviewed modules into an isolated implementation change while preserving unrelated PR #268 and the current released v2 baseline. Ensure original signed-off requirements remain unchanged.

## 4. Conclusion and required next action

**Final D1 design verdict:** **Compatible after documented design/rollout revisions; no unresolved approved-product scope conflicts.** However, *implementation compliance is NOT established*. Key prerequisites are actual session unification, server-side CSRF/identity checks, PWA/gateway origin/service-worker integration, sandbox write authorization with App custody, genuine hosted test-byte verification on the production origin, source-aware validation, D3–D5 user features and D6 real-device/rollback/production acceptance.

**Next:** D2 code-only implementation of the one-session guarded API/operations contract with write flag hard-off and adversarial security tests. No more speculative per-change attestor work. Owner has approved the **production-first deployment strategy**, but explicit approval is still required before injecting write-capable secrets, enabling a route that accepts real writes, mutating public canonical content or conducting the final user-facing V3 cutover. Avoid more P3-N subphase numbering.
