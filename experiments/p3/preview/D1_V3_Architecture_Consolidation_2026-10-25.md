## 1. Architecture selected: one same-origin owner-facing service, one automated publishing path

The public Fishing Companion retains its **anonymous, static canonical GitHub Pages release**. An approved **same-origin Cloudflare gateway** serves its unchanged, integrity-verifiable Pages bytes at **`/fishing/`** and serves owner OAuth, a 7-day first-party session and the future `/api/v3/` publishing/status API at **the same HTTPS origin**. This is the P1 AUTH-P0 architecture that passed real installed Android and Windows testing and was accepted for feasibility with documented waivers on October 22. It is **not** the current `ginosega.github.io` origin; production V3 URL and installation migration require explicit final cutover approval.

For the *minimum D2 sandbox slice*, the **intended production Cloudflare gateway Worker runtime** is the only owner-facing entry point and the only future GitHub App token custodian. The owner explicitly approved using the production hosting environment for iterative V3 development and accepted temporary site downtime; no second hosted V3 preview site is required. This is a revised rollout strategy, **not** permission to mutate canonical production data or expose unfinished write endpoints before their security gate. GitHub App signing material is a **Cloudflare encrypted Worker secret**, never a browser token, GitHub Actions secret, project file, public asset, or ChatGPT value. A dedicated server-only adapter issues **brief, repository-ID-scoped installation tokens with explicit per-request permissions**. This is an *architecture assignment*, not a claim that the PEM is presently bound to that Worker. No new key, attestor or per-change human signature is part of V3.

- **Read path:** anonymous `GET /fishing/*` proxies canonical Pages with strict path/host/redirect/body rules; preserve exact release bytes, service-worker cache eligibility and offline integrity. Never forward browser session cookie/OAuth credentials upstream to Pages, reflect `Set-Cookie`, or inject app script into the hashed release. Private API responses are `Cache-Control: no-store` and not cached by the PWA service worker.
- **Owner auth:** `GET /auth/start`, `GET /auth/callback`, `GET /session`, `POST /session/signout`, `POST /session/revoke-all` use the **existing** AUTH-P0 GitHub OAuth callback/verified numeric owner identity, 7-day **absolute, non-sliding**, `Secure`+`HttpOnly`+`SameSite=Lax`+`__Host-` first-party cookie and D1-backed per-request revalidation. OAuth GitHub identity token is consumed for identity only; never authorize a repo write based on a client-provided identity.
- **Privileged accept:** `POST /api/v3/operations` requires a valid owner session **plus a session-bound anti-CSRF token** returned to the authenticated owner via same-origin `GET /session`. Check exact HTTPS origin, strict same-origin Fetch Metadata for privileged actions, method/content type, explicit intent header, bounded body and server-owned repo allowlist. Reject missing/unusual headers for privileged writes even if the legacy AUTH-P0 signed-out signout route accepts absent Fetch Metadata. No automatic owner consent/signature ceremony on each Save and Publish.
- **Durable operation:** write an idempotent Accepted record + validated bounded payload snapshot to private isolated D1, unique by owner ID + allowed repository ID + idempotency key; return **202 Accepted** and stable operation ID immediately. A page may close after Accepted. D1 transactions/leases own all state; retry or uncertain receipt cannot create duplicate PRs. Lost acknowledgment = **Unknown until server-side status reconciliation**, never unconditional resubmit. Owner-only `GET /api/v3/operations/{id}` reads persistent status.
- **Private automated worker steps:** an explicitly enabled scheduled task/guarded continuation reads its own D1 leases, obtains the *current* GitHub source revision, applies source-aware canonical conflict rules, constructs a cohesive branch commit, creates a content-only PR, waits for **exact head + expected base + genuine required CI**, handles a moving base by revalidation rather than force-push/bypass, merges only through normal GitHub permissions/rulesets, and observes the existing production workflow's **actual hosted byte/release identity** before `Live`. User-facing states: Editing → Saving → **Accepted** → Validating → Publishing → Verifying → Live; plus Conflict/Failed/Pending/Unknown where applicable. An accepted D1 operation is **not** a merged, deployed or Live publication.
- **Target selection / production-first distinction:** D2 initially targets **only** immutable private `ginosega/fishing-p3-sandbox` repo ID `1430581407`, owner ID `265665562`, using the **same intended production Cloudflare hosting environment**, not a separately maintained preview website. Isolate testing by immutable repo ID, owner-only feature gates, isolated D1 operation data and test-only content/paths on the production origin; do not mingle sandbox test records with canonical public Gear/KB/Catches. A successful merge into the private repo is *not* a hosted publication: D2 must independently verify sandbox-derived published test bytes/release lineage from the actual intended production-origin path, or mark hosting verification blocked and explain the measured alternative. No production public-main GitHub write, live owner-facing origin change or broad enablement occurs without a distinct consequential authorization and verified rollback.

**No parallel command-control framework:** the P3 Access-ingress/bridge static-503 Workers, OIDC-only runner approval, HMAC transport, ECDSA human operation approver and independent P3-41 attestor **are not dependencies** of this ordinary owner-session Save and Publish path. Keep existing disabled Workers disabled; do not casually install the research proof envelopes or copy old secret-bearing workflows into the new gateway. A narrower private service binding may be adopted only if later demonstrated necessary, with separate security review; it is **not** the default D1 architecture.

## Production-first variance and signed-off-product guardrails (October 25 owner decision)

**Approved scope change:** The owner affirmatively accepted production hosting for V3 development, including downtime, **instead of configuring and maintaining a separate nonproduction preview website**. This changes the P3/P4/P8 staging methodology in the originally approved implementation plan; it does **not** remove any V3-AUTH/SAVE/UPLOAD/CATCH/VIEW/CONNECTION/PERF/UPDATE/DRAFT/OPS/X requirement, authorize premature public-data writes, waive live hosted-byte verification, or waive the separate final V3 cutover decision. The approved October 19 requirements, design and UX documents remain unchanged as signed-off product contracts. See [D1 requirements compliance audit](D1_V3_Requirements_Compliance_Audit_2026-10-25.md) for explicit crosswalk, conflicts and follow-through.

**Protected existing release:** Preserve the known-good V2 GitHub Pages source, release identity, manifests, image bytes and normal content history as a recoverable fallback. A temporarily unavailable frontend is acceptable, but data loss, secret exposure, bypassing `fishing-merge-ready`, breaking canonical source references or claiming an unverified update Live is not. The first operation targets only the isolated private sandbox and test data, even though the website host is the intended production environment. Use an exact isolated test pathname (not a second host), feature gates, dedicated D1 operation state and rollback/redeployment evidence. The final release must still work at the agreed V3 address, preserve a viable rollback, and receive explicit production cutover approval.

**UI behavior cannot regress:** Anonymous default; discreet Sign In **only** at the bottom of Connection Status; unobtrusive valid-session restoration; no standalone owner URL; one Save and Publish without per-item signature/confirmation; online only; conflict/recovery and Accepted vs Live; ordinary Catch schema without new photos; image uploads and Knot sequences; Work Offline preference and verified cache, Markdown Picture Viewer; retained FISH108 exact-hosted release verification; safe optional local draft removal decision. D1 chooses a backend architecture, not a reduced V3 scope.

**Session safety:** P1 and P3 prototype cookie/session/hash/table formats are incompatible. The unified backend must use a single owner session backed by one authoritative session store and bind privileged POST CSRF strictly to that server-validated session. A `GET /session` CSRF token is public only to the same authenticated owner context and must not appear in anonymous responses, caches, Pages proxy requests, GitHub Actions or logs. The original G1 accepted seven-day revocation exposure only for P1 feasibility; all actual V3 writes must pass complete fresh per-request authorization and negative security acceptance.

## 3. Concrete minimum D2 HTTP contract (design, not installed endpoints)

| Method and route | Who | Result / restriction |
| --- | --- | --- |
| `GET /fishing/*` | Anyone | Byte-identical publicly readable Pages release through same-origin gateway. Immutable static release caching only; no auth required. |
| `GET /auth/start?return=/fishing/`; `GET /auth/callback` | Anonymous initiating OAuth | One-use PKCE/state, strict return allowlist, only authorized numeric owner creates first-party session. |
| `GET /session` | Anyone | Anonymous boolean only; owner receives `authenticated, authorized`, short-lived CSRF token and compact identity, `no-store`. No OAuth token, session secret, installation token or signing key. |
| `POST /session/signout`; `POST /session/revoke-all` | Validated owner/session as appropriate | Use previously accepted AUTH-P0 lifecycle policy; privileged revoke-all requires CSRF/intent. |
| `POST /api/v3/operations` | Owner session + CSRF + strict same origin | Small, canonical source-aware package (D2: *one Gear text edit only*, empty media) and idempotency key; bounded limits; returns 202 Accepted + operationId/status URL. No browser-supplied repo URL/path/head as authority. |
| `GET /api/v3/operations/{id}` | Same owner session | Durable current state and safe PR/CI/release identifiers; no raw tokens, confidential logs or staged binary bytes. |
| Internal scheduled task | Trusted Worker runtime only, **no public HTTP route** | Lease work, validate candidate, GH App PR, exact CI, ordinary merge, hosted proof; security-gated and default OFF. |
| All other POST/PUT/PATCH/DELETE routes | Nobody | 404/405/403; no generic GitHub proxy, arbitrary source upload or GitHub Actions dispatch endpoint. |

The test-only `POST /api/v3/operations` does **not** start accepting real data on saving this Markdown. The existing v2 editor still uses Copy Changes until the D3 owner UI is built. During D2, sandbox-scoped publication test bytes may be served under the intended **production-origin test-only path**, but they are **not** public canonical content, not proof of a real production publish, and must never be displayed as a user's canonical Live item.

## 4. GitHub App permissions, protected branch and repo correctness

**Owner-reviewed *historical sandbox* GitHub App installation rights:** `contents:write`, `pull_requests:write`, `checks:read`, implicit `metadata:read`, selected private repository. Earlier local App diagnostics and App-JWT-authenticated GETs support that installation, but the current GitHub connector **cannot fetch** `GET /repos/{repo}/installation` and **cannot confirm current live grants**. Reconfirm in a guarded *read-only* provider preflight before any installation token mint/write, and never substitute the GitHub connector's own repository permissions for the dedicated sandbox App grant. No assumption the same App is installed on public `ginosega/fishing`. Do not request `administration:write`, `actions:write` or branch-protection bypass.

**Exact fresh public-main ruleset inspection:** [`ginosega/fishing` ruleset #25742040](https://github.com/ginosega/fishing/rules/25742040), active, applies `~DEFAULT_BRANCH`. Requires **a PR**, **strict (up-to-date) status checks** and exact required status context **`fishing-merge-ready`** from GitHub Actions App integration ID **15368**. Required approving review count is **zero**, no mandatory code-owner/last-push approval, all merge methods allowed, no configured bypass actors, force updates/deletion denied. `require_extra_approval_for_unattributed_changes=true` is a GitHub *Copilot-only* extra-approval rule and does not require approval when baseline required count is zero per GitHub documentation; still verify real GitHub PR mergeability rather than assuming. This appears compatible with the approved **automatic** Save and Publish **if** the App is allowed to merge normally **after** that exact check passes on the latest current-base-tested head. Never fake the `fishing-merge-ready` check, use an arbitrary check app, bypass a ruleset, or merge after the base moves.

Public-main `/branches/main/protection` returns **403 Resource not accessible by integration** via current GitHub connector; no claim that all possible branch-protection overlays have been exhaustively inspected. The private sandbox ruleset list returns **403 GitHub Pro or public required**, and private branch protection likewise **403**; its existing `validate-sandbox-head` isolated CI was previously validated, but actual merge permissions/rules must be read and confirmed on an authorized D2 preview operation.

Before any real GitHub write at D2, confirm: target repo immutable ID, dedicated App installation ID/current grants, branch/ruleset merge policy, exact trusted CI source and check origin, and approved Cloudflare Worker secret custody. **Stop for explicit authorization before adding/binding the App PEM or enabling sandbox write routes.** Even a one-repo installation token inherits only the explicitly requested subset of current App grants, never more; validate its actual response against those exact permissions and repo ID.

## 5. Durability, automated progression and Free-tier economics

A GitHub CI workflow may take longer than a browser request. Do **not** keep one Worker request open until final hosted verification, rely on a browser tab staying open, or infer Live from a PR merge. Use bounded, lease-protected D1 state transitions and **one guarded continuation step per scheduled invocation** (or another equivalent durable scheduler if operationally verified). The scheduled handler is not an HTTP caller bypass, never authorizes new operations, and processes only already owner-accepted, authenticated D1 submissions. A state may remain Pending/Unknown and must be re-read safely after errors or lease expiry.

Current [Cloudflare Workers Free limits](https://developers.cloudflare.com/workers/platform/limits/) (published October 12, 2026) include **10 ms CPU/request**, **50 subrequests/request** and **5 Cron Triggers/account**; [Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/) support scheduled `scheduled()` handlers. These are **real D2 feasibility constraints**: test actual CPU/subrequest usage and Cron availability before claiming the Free service can run the end-to-end automation, large media handling or canonical source validation. Move expensive canonical validation to the existing GitHub exact-head Actions check where possible. If the minimal D2 slice exceeds limits, stop and present the measured alternative/cost for approval; **do not silently upgrade Cloudflare** or add unexplained paid infrastructure.

Keep AUTH sessions and content operations separately isolated in D1, with operation rows, leases, idempotency, PR/CI/merge/hosted receipts and bounded audit only. Check recovery after a Worker restart and client tab closure. Status GET is owner-only and no-store. Under the approved production-first revision, **do not create a second hosted preview website**. The D2 test instead requires test-only release bytes at an isolated path on the intended production Cloudflare origin, verified against the exact sandbox PR/merge/check/asset identities; if that cannot be established safely, D2 is blocked until a narrowly scoped alternative is reviewed. A private GitHub repository's Pages hosting availability must not be assumed.

## 6. Mandatory negative/security tests inside D2 (not new P3-N subphases)

1. Anonymous/wrong GitHub numeric owner, expired/revoked session, forged/missing CSRF and cross-site/missing Fetch Metadata **cannot create any D1 operation or trigger GitHub App token requests**.
2. Spoofed browser repo IDs/head/path, status ID enumeration, invalid canonical record and unsafe Markdown/media paths are rejected. Source-aware concurrent edits preserve newer unrelated changes; conflicts preserve the author's draft.
3. Failed/denied App grant, wrong selected repo or unexpected App permission never attempts a write; installation tokens do not appear in app payloads, Worker logs, Actions logs or public artifacts.
4. Double Save/reload/tab closed, lease expiry/restart, ambiguous PR creation response, interrupted CI or moved base are idempotent and never create silent duplicates, force updates or false Live.
5. Only genuine exact-head `validate-sandbox-head` in sandbox and later genuine `fishing-merge-ready` on public main may authorize normal merge; protection incompatibility is a STOP, never bypass.
6. No private GitHub/Cloudflare/App keys reach the public PWA, no auth/Cookie header is proxied to Pages, no privileged response caches in the PWA offline library.
7. D2 must prove **real** allowed text-only sandbox PR → latest-head checked CI → normal merge → test-only **byte-identical release hosted on an isolated path at the intended production gateway origin**. Verify the exact asset/commit lineage, never claim canonical Live based on sandbox test hosting. Later public-main production publication requires its own ordinary PR/CI/hosted verification and specific authorization; sandbox evidence alone never authorizes public-main writes.

The source-only P3 440/440 test suite is a regression baseline but is **not** a substitute for these D2 live integration cases.
