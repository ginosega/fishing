# FISH118 / AUTH-P0 — Session transport and hosting decision brief (2026-10-22)

**Status:** technical options assessment and recommendation for an *isolated, read-only next feasibility proof*; **NOT** approval to relocate production, adopt a custom domain, install the GitHub App, enable write permissions, incur charges, or proceed to P3 publishing/P4 integration. Remains in draft PR #262. Production `main` and GitHub Pages are unchanged.

## Decision in one paragraph

The existing `https://ginosega.github.io/fishing/` static PWA and `https://fishing-auth-p0-test.ginosega.workers.dev` API have **different origins AND sites**. The successful owner-authentication test on the Cloudflare **first-party** origin is valuable but does **not** prove that the Pages app can send or restore that session. Credentialed CORS never overrides third-party cookie restrictions; a `SameSite=Lax` session cookie does not accompany ordinary cross-site JavaScript `fetch` calls. Therefore **do not implement the production Pages PWA → workers.dev API using third-party session cookies**.

**Recommended next step (not yet approved):** add an isolated, read-only Cloudflare Worker gateway at the *existing test origin* under `/fishing/`, serving the **unmodified** published GitHub Pages bytes and exposing existing OAuth/test-session endpoints on the **same HTTPS origin**. Validate the full PWA, installed-Android return, offline library and exact release/byte identities through this gateway. The canonical authoring repository and existing Pages publisher remain unchanged. Only after that proof should the owner decide whether a **new app URL/installed PWA** is acceptable. No immediate v3 hosting cutover or repository publishing credentials.

## Verified baseline and evidence boundary

- User-reported Oct 22 Windows Edge ordinary browser: authorized GitHub OAuth; survived new tab and Edge restart.
- User-reported Oct 22 Android Chrome browser and genuine **installed** Android Chrome PWA: owner login; OAuth initiated *inside* PWA returned to installed PWA; sign-out reflected in refreshed Chrome; session survived app closure/relaunch and phone restart.
- Cloudflare Worker at `fishing-auth-p0-test.ginosega.workers.dev`, D1 sessions, OAuth-only GitHub App, no repository installation, no write endpoints. On that origin, opaque session cookie is `Secure; HttpOnly; SameSite=Lax` and host-only (`__Host-` name).
- iOS skipped at owner's request (no iPhone); Android Edge, unauthorized *real* GitHub account, token expiry, live revoke-all and blocked-third-party-cookie field cases have **not been validated**.
- Same-origin standalone harness is **not** the original Pages site's release-aware service worker or offline library. The latter is an explicit acceptance gate.
- Baseline production full-release workflow #543 (Oct 21 checkpoint), hosted release `131ebca9c6d46fa1c1d815ad43a318f6`, originally 577 files/100 Gear/60 KB/12 Catches. Reinspect live source/production before making any change; this document does not assert these are indefinitely current.
- On current source, the browser's loader registers its service worker with a root computed from its page URL; the build produces relative manifest `start_url: './'`, `scope: './'`. This makes the unchanged `/fishing/` path on a different origin technically plausible, **not field-proven**.

**Important nuances:** The application can serve **public reading** on the old Pages URL forever, but a proxy-origin installed PWA at a different URL has separate service workers, IndexedDB, caches, storage permissions and installation identity. The canonical repository is the *only editable content store* in both options A and B; D1 stores only sessions/operations, not Gear/KB/Catch canonical records. A new proxy hostname cannot set the existing `ginosega.github.io` cookie, nor can the GitHub Pages origin set the Cloudflare host cookie.

## Recommended A: narrowly scoped next proof (G1 remains open)

1. **Approval boundary:** ask owner to authorize only a disposable, read-only test route `/fishing/` on the existing test Cloudflare Worker, with **no production URL change**, GitHub App permission change, additional vendor, purchased domain or repository write.
2. **Routing:** pin upstream to `https://ginosega.github.io/fishing/` and explicitly allow public GET/HEAD content paths. Map `/fishing/*` to the identically pathed GitHub Pages URL (avoid changing application bytes or relative references); isolate `/auth/*`, `/session*` and any future write path **outside `/fishing/`**. Refuse arbitrary proxy targets, methods, redirects to unsafe hosts, open redirects, or mutable upstream configuration.
3. **No credential leakage:** make upstream server-to-server requests without browser session cookies, Authorization headers, client credentials, or D1 secrets. Never forward `Set-Cookie` from upstream. Preserve appropriate static content types and immutable/release cache semantics; do not cache private auth/API responses. Protect cache keys, no-store session operations and trusted-source validation.
4. **Release and byte fidelity:** for the current published release, compare byte hashes for `release.json`, manifests, app JS, CSS, image content and KB/Gear/Catches JSON to GitHub Pages. Verify count and exact release identity. Check range/HEAD semantics only if needed. Test coherent transitions after new publication, offline readiness/second reload and dirty editor protection (FISH116).
5. **New PWA acceptance:** install **the test gateway's real Fishing Companion PWA** on Android (not just AUTH-P0 harness), check path/scope, automatic session, in-app OAuth callback return, sign-out and session persistence over restart, Work Offline and verified prepared-library behavior. The old production PWA and its prepared offline data remain completely untouched. Record that the *new gateway-origin library must be prepared independently*.
6. **Security acceptance:** same-origin `fetch` with default credentials and host-only HttpOnly Secure SameSite Lax cookie; strict Origin/Fetch Metadata and CSRF on mutating methods, numeric owner authorization on every write (future), exact hostname restrictions, explicit denied-user/revoke-all/expiry handling, no third-party dependency. Verify anonymous URLs and unauthenticated writes fail. No GitHub write route in this feasibility step.
7. **Operational acceptance:** Cloudflare Free request/CPU/D1 quotas, latency/image behavior, errors/retries and fail closed for auth; keep browser performance, byte-for-byte release verification and proxy troubleshooting measurable. A future v3 cutover needs **separate explicit user approval**, a new installed PWA/URL migration and offline library preparation plan.

**Go/no-go:** A is a *candidate* not yet validated. If the proxy fails release integrity, SW/offline behavior, real installed-PWA sign-in or performance/quotas, do not proceed to P3. Reassess option B or C with the owner. If A works but the user wishes to **keep the existing installed app URL/identity**, that preference alone may rule out A for production.

## Formal decision gates

**Immediately approved by the user earlier:** Cloudflare Free/GitHub App OAuth-only nonproduction test and the already completed same-origin harness field tests.

**Not approved as of writing:** deploying additional static gateway routing; adopting a different launch URL; using a purchased custom domain; browser-held application session tokens; GitHub App write permissions or installation; P3 publishing service; v3 production cutover. Ask explicit authorization for each material change before doing it.

**Suggested decision for the owner:** *“May we extend the existing Cloudflare AUTH-P0 test Worker with a read-only `/fishing/` proxy of the existing published site, test installed Android auth/offline/release behavior on that new test URL, and keep the actual Pages site and existing installed PWA untouched?”*
