## Delivery controls

- **No isolated-component queue.** Every new implementation PR identifies WP owner, requirement(s), dependency, failure coverage and exit evidence. A component is complete only when integrated and tested; an isolated unit-test pass is not a completed WP.
- **One active package by default.** Work is sequential unless a separate change is genuinely independent and does not bypass a gate. Work may take several bounded PRs, but no new V3 milestone/feature/release gate or redefinition of exit criteria without documented evidence, impact and explicit owner approval.
- **Evidence states:** source implemented → exact-head CI passed → private hosted/byte verified → owner field accepted → separately authorized public Live. A read-only real-record staging package is **not** the full RC; a GitHub PR or HTTP 201 is **not** published.
- **Release blockers:** unresolved source/identity, canonical file/media drift, unresolved unknown publication, missing owner authorization, red required checks, insecure session, broken offline/draft safeguards, inadequate fast progression or false hosted proof. Stop or fail closed; do not weaken tests.
- **Explicit exclusions:** multi-user, offline publish queue, new content schema, inline Notes-image derivative optimization (#301), broad prototype import (#263), mandatory V2 parallel running/full rollback rehearsal. Historical #287 is investigated if a current failure recurs, not automatically a new workstream.
- **Change control:** cite relevant accepted/rejected/deferred/superseded decisions. A newly discovered issue is assigned to WP0–WP6; if it cannot fit, report the conflict and obtain owner approval before expanding scope.
