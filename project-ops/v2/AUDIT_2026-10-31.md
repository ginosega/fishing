## 3. Authority mapping and identified drift

### Three distinct authorities must remain separate

1. **Approved intended behavior:** signed-off requirements/design/UX/implementation plan, plus subsequent owner-approved amendments. Approval records hold **point-in-time** consent, not automatic consent for future provider operations or release.
2. **Implemented source:** exact Git commit/tree, PR diff, source tests and CI results. Source green is not equivalent to deployed or field-accepted.
3. **Running reality:** GitHub/Pages/Cloudflare deployment identity, hosted bytes/release, private Worker version, user field acceptance. Each requires independent evidence at the time of a consequential action.

GitHub is the durable system of record for versioned artifacts **and pointers to operational evidence**, not a magic substitute for querying Cloudflare or the user's device.

### Concrete drift/gap observations

**A1 — Same current status duplicated in many files (high).** Five different documents contain repeated state and action language. A change requires coordinated multi-file edits or risks inconsistent answers. **Fix:** one in-place authoritative `CURRENT_STATE` per workstream; other documents link instead of copying.

**A2 — Chronological accumulation makes old commands look current (high).** Historical `README`, Context, TODO, Decision Log and Bootstrap retain previously labeled "current"/"final" gates and alternative next steps. **Fix:** archive the dated record untouched; current entry point contains only live status and links. Old instructions explicitly lose active routing authority after cutover.

**A3 — Approved baselines mixed with later amendments (high).** `pwa/docs/Fishing_Companion_v3_Requirements.md` is labeled approved October 19 but has October 31 feature/field-status paragraphs prepended and includes the October 27 V3-SAVE-09 approval. The separately signed October 19 approval record correctly applies to the original exact blob; later owner-approved changes are **not** retroactively part of that original signature. `Implementation_Plan.md` also has a later Notes amendment at the top while retaining October 19 handoff preconditions. `Fishing_Companion_v3_Notes_Editor_Amendment_2026-10-31.md` itself starts with field failures before permanent requirements. **Fix:** retain approved original baseline and approvals; use separately dated/ID'd amendment records with an index showing effective precedence. Do **not** silently rewrite product behavior under this docs refactor.

**A4 — Handoff rules conflict with the desired bounded startup (high).** `pwa/docs/README.md` explicitly tells a new session to read all five root files in order; `D1_V3_Architecture_Consolidation_2026-10-25.md`, `FISH118_V3_Finite_Delivery_Reset_2026-10-25.md`, and root Bootstrap tell the user to paste the **entire** bootstrap at transfer. Those were genuine instructions for the older operating model, but unsuitable as future active guidance. **Fix:** formally supersede just the *handoff protocol*, retaining historical provenance and all material safety gates; record owner acceptance of the new protocol.

**A5 — Work item lifecycle is mixed into design, decisions and TODO (medium/high).** Active bugs, implementation tests, deploy prep, accepted UI behavior and old milestone narratives are woven together. Prior `P3-N`, `D1–D6`, `P0–P8` and `FISH-TODO-###` names serve different levels, so more new parallel numbering increases ambiguity. **Fix:** map each active outcome to one issue/work item with stable ID, explicit acceptance and an independent state; link to inherited V3 milestone and requirements. Do not renumber historical work or re-open completed milestones.

**A6 — Hosted and source status can be conflated (high).** Gear Notes SHA-indexing and Catch picker are source-validated yet their latest private rollout and field results are not independently verified. Older source-only files contain stronger historical "not implemented" language. **Fix:** separate columns for implemented source, exact-head CI, deployed private/public, field acceptance, blockers, and evidence freshness; absent current evidence = `unknown` rather than inferred.

**A7 — Documentation CI lacks semantic protections (medium/high).** `.github/workflows/fishing-production.yml` has a documentation lane for Markdown-only PRs; its sole docs validation step is `git diff --check` (whitespace). It does not check authority references, limits, required status fields, cross-links or active-state consistency. `fishing-p3-source-validation.yml` is source/sandbox-test focused, not doc governance. **Fix:** first design a small deterministic doc verifier; **important caveat:** changing YAML or adding executable tooling invokes the Full Application Release lane under FISH108, and is outside the charter's initial docs-only-only change restriction. Plan a separate authorized workflow/tooling change or first use a manual/read-only checker. Never quietly alter release CI on a docs-only approval.

**A8 — Main/development/document-branch visibility (medium/high).** The public default branch is `main`, while working V3 state is on draft `feature/fish118-p3-mock-publisher` with a separate docs PR based on it. A newcomer who reads only default `main` can miss more recent unmerged V3 state. **Fix:** entry point explicitly names *current feature branch*, exact verification time and source commit; validate branch ref before consequential work. Do not publish the unmerged feature branch as if it were deployed main.

**A9 — One-off handoff/report documents already carry useful evidence (medium).** `pwa/docs/` has a historical-record notice and separate sign-offs; `experiments/p3/preview/` includes independent D1 architecture, D2/D3/D4, migration, and provider/security reports. **Fix:** preserve and index rather than rewrite/re-copy, keeping special sensitive setup instructions out of normal boot.

**A10 — No proof that chat errors were caused by context size (unknown).** Small project-chat messages and bounded GitHub retrieval passed. Earlier large recovery messages failed. Correlation motivates economical retrieval but does not prove platform root cause. **Fix:** cold-start tests plus Support reporting if errors recur, never an assurance that Markdown cleanup prevents service errors.

## 6. Proposed migration sequence and open gates

1. **P1 owner-reviewed design:** agree directory names, owner of current-state changes, evidence freshness/unknown treatment, template fields, mutable-current vs immutable-approval policy, supersession conventions, and workflow automation scope. Resolve the docs-only vs CI-tooling constraint explicitly.
2. **P2 zero-loss preservation:** keep complete existing files and their Git history; record immutable source commit and coverage mapping. Do not prune originals until every durable category has a new owner/index.
3. **P2 one-time reconciliation:** read the *latest* relevant branch/CI evidence and externally verified hosted identity separately; do not copy old "deployed" statements into active fields. Leave all unsettled states unknown/pending.
4. **P3 validation:** deterministic document schema/size/checklist/link checks, manual safety coverage review, diff confirms no application code or deployment config changed in docs migration. Any future workflow change separately reviewed under FISH108.
5. **P4 cold-start test:** fresh Fishing-project chat, no old Bootstrap/past chat retrieval, reads only bounded entry/status/queue; must identify V3 branch and PR, actual evidence gaps, two major defects, release owner gates, next safe action; compare answer with external source audit.
6. **P5 adoption:** owner sign-off, reviewed documentation cutover (branch comparison and merge strategy reconciled against concurrent changes), V3 resumption only after safety state is refreshed.

## 7. Known limitations and pending checks

- **No provider live-state proof** from this audit. It is unsafe to mark private Notes image fix as deployed without Worker version + controlled field test. Catch draft/receipts must not be resubmitted blindly.
- **No comprehensive semantic interpretation** of all 265 Markdown files; the repo-wide tree inventory is complete at this commit, while semantic analysis targeted the *governance documents that control startup, approvals, release and V3 status*.
- **Do not rewrite original October 19 approval records** to imply they consented to October 27/31 amendments; maintain provenance links.
- **Do not automatically replace** v2/full-release tests with docs validators. Document-only changes are currently gated differently and should be addressed as a separate engineering policy decision.
- **No automatic deletion, merge, live site deployment, Cloudflare/D1 operation, provider permission modification or V3 feature work** is part of this audit.

**P0 conclusion:** The refactor is warranted. The next actionable output is a **small P1 design/ownership proposal** informed by the accompanying [migration coverage matrix](MIGRATION_COVERAGE_MATRIX.md), not an immediate archival purge.
