# ADR-0011 — Simple direct-save V3; preserve approved UX

**ID:** ADR-0011
**Status:** accepted in principle — explicit owner architecture pivot, November 19, 2026; source implementation and provider migration NOT approved by this record
**Scope / search tags:** V3 simplification, direct Save, D1 content, GitHub publishing superseded, approved UX, WP3 H2 freeze
**Original evidence / approval:** [FISH-TODO-118 decision in issue #377](https://github.com/ginosega/fishing/issues/377#issuecomment-7016821059). The owner asked to stop recursive publishing/recovery complexity, retain the already-approved V3 UX, and accepted abandoning GitHub as the canonical *content* database.

**Decision:** Build the smallest viable single-owner Fishing Companion: **sign in → edit → Save → reload/view persisted data**. Preserve approved V3 Gear, Knowledge, Catch and Notes user experience, links, media, local draft protections, offline read-only functionality and anonymous reading. Use the existing GitHub OAuth owner sign-in initially because it is already tested, but do not require a GitHub PR, CI, merge, Pages build or ChatGPT JSON handoff for ordinary record edits. Keep GitHub for versioned **application code** and governance, not the authoritative mutable fishing records. The intended authoritative mutable content store is Cloudflare D1 behind an authenticated same-origin Worker; existing static image URLs remain readable and an object store is introduced only if needed for new uploads.

**Minimal behavior:** Validate owner session and CSRF; validate a supported record; save one record with expected-revision conflict protection to D1; return success only after durable write; next online GET shows the updated record. Conflicts reject with a clear message and preserve the user's local draft. No asynchronous publish queue, general offline editing, per-edit GitHub writer, staging ON/OFF Worker switch, watchdog, Task Scheduler, operation step fences, or cloud recovery service. Keep source-code CI, basic security tests, and an uncomplicated content backup/export before migration; do not build a second publishing platform. Avoid a new authoring user interface or a second canonical datastore.

**Supersedes:** Original V3 requirement to keep GitHub canonical for Gear/KB/Catch/Notes and source images **for user authoring** (ARC-001 portions; original Requirements §2.2). The FISH108 GitHub PR/CI/deploy and public byte-check path (PUB-001/002/003/006) remains applicable to **application-code releases**, not to each D1 content Save. The old Save-to-PR ≤60-second public-GitHub-release definition is replaced for in-app edits with successful durable Save and an immediately retrievable online record. PUB-004's meaningful protection against lost updates remains as simple revision/409 handling; no durable publisher-operations workflow is required. All older approvals remain historically documented, not deleted.

**Stop work:** Freeze WP3 H2/H3 GitHub publishing PR stack and synthetic-PR acceptance, Worker ON/OFF recovery/Cloudflare scheduling, and Windows canary investigations. Existing drafts stay archived/unmerged, original task evidence stays untouched. Do not continue the old WP3–WP6 implementation sequence unless owner expressly reopens it. This is a deliberate simplification within FISH-TODO-118, not another numbered package.

**Delivery and acceptance (three finite checkpoints):**
1. **Direct edit slice:** Reuse the approved UX and WP2 login; implement one isolated authenticated D1 Gear record Save/read/reload with a simple 409 conflict test. No new media service needed for this first slice.
2. **Other records and assets:** Extend the same endpoint to KB, Notes and Catch; preserve existing links/images; implement new-media upload only if necessary for the already-approved UX. Include basic export/recovery.
3. **One-time migration and owner acceptance:** Inventory the current authoritative GitHub records and images, take a recoverable snapshot, import and reconcile record IDs/links/assets without losses; owner verifies real Gear/KB/Catch data, direct Save and reload in Windows Edge and Android. Separate explicit approval before new provider resources, permission changes, schema/data migration, app merge, public route changes or V3 cutover. Public V2 remains unchanged before cutover.

**Alternative considered / why rejected:** Continuing GitHub source-publishing with synthetic PRs, many operation receipts and an independent watchdog did not achieve a real user-facing Save after prolonged failures. A battery-powered tablet is unsuitable as an unattended independent OFF supervisor. Swapping in another scheduler merely carries the complexity forward. Full user-account/multi-user, new unrelated fishing features, offline write queues and simultaneous dual canonical sources also remain excluded.

**Reconsider only if:** Direct D1 Save cannot satisfy preservation of the owner's approved UX, data safety and existing records, supported by a concrete failing test and a specific later owner decision. Do not add resiliency layers for hypothetical failures.

**Evidence boundary:** This ADR records an approved architecture direction only; no D1 content schema, new R2 bucket, provider write, data migration, deployment or user Save is yet proven. Do not claim that V3 has shipped.
