# ADR-0012 — Unified V3 content storage and independently versioned offline snapshots

**ID:** ADR-0012
**Status:** accepted architecture direction — owner decision November 20, 2026; implementation/deployment gates remain open
**Scope / search tags:** D1 online catalog; legacy V1/V2 content; R2 private content images; revision-safe Save; Gear KB Catch; offline content snapshot; FISH091; Android Edge; V3 consolidation
**Original evidence / approval:** [FISH-TODO-118 owner direction and acceptance receipt](https://github.com/ginosega/fishing/issues/377#issuecomment-7058493017), following [architecture audit](https://github.com/ginosega/fishing/issues/377#issuecomment-7057662827) and accepted [ADR-0011](ADR-0011.md).

**Decision:** Make **D1 the single authoritative online store for Gear, Knowledge Base and Catch structured records and Markdown**, and **private Cloudflare R2 the single content-image store for both historical V1/V2 assets and all future V3 photos**. Existing source photographs must be inventory-hashed, copied, reconciled and retained as archival/rollback sources until field acceptance; no permanent dual image reader in final V3. Preserve Gear/KB/Catch logical record and content-image paths where safe. Use one owner-authorized, expected-revision D1 Create/Edit/Save architecture with optional transactional R2-media references. Existing immutable software releases retain JS/CSS/UI icons, but **current fishing content changes independently from software releases**. Final access policy: anonymous published content reads (including verified referenced images) and explicit offline preparation; owner-only Add/Edit/Save and media upload, no offline Save. [Owner decision](https://github.com/ginosega/fishing/issues/377#issuecomment-7178253882).

**Offline:** Preserve the accepted FISH091 service-worker and Cache Storage foundation, explicit reader-triggered **Update Offline Library** (signed in or signed out; SEC-001), Work Offline read-only state, verified hashes/bytes, complete generation selection, last-known-good snapshot retention, abort-on-corruption/quota/failure, no mixed content generations and protection of unsaved drafts. Replace the current release-bound *content* library with independently versioned, compatibility-checked **snapshots of a consistent D1 record+Markdown graph and all its referenced R2 images**. Incrementally reuse already verified unchanged objects; do not silently download the entire content library during ordinary application startup. A content snapshot's identity and freshness are distinct from software release identity. A browser storage eviction requires readiness re-verification, not a false Ready indicator. Automatic online mode reads D1; Work Offline reads the last complete verified snapshot without network calls.

**Other consolidation:** Include direct owner Add parity for Gear and KB, full current-content online catalogs (remove permanent 100/60/12 maximum/frozen overlay), one authenticated Save path for text-only and media edits, shared card-thumbnail pipeline independent of software rebuild, safe local draft recovery based on data versions, and removal of obsolete V2 GitHub handoff/publishing branches from final V3. Preserve public V2 unchanged until a separately approved V3 cutover.

**Prior decisions preserved:** Supersedes the *runtime* assumption in [ADR-0011](ADR-0011.md) that legacy static images may remain V3's permanent content source, and the premise of FISH091 that the fishing-content snapshot and application release must be one version. Does **not** supersede ARC-003/004/007/008, the original immutable software-release security, REL-001's explicit offline preparation, REL-002 provisional drafts, REL-003 release coherence, REL-004 approved card thumbnails, or REL-007's separately deferred inline Notes image derivative optimization. Excluded: general offline editing/publish queues, multi-user account system, two canonical editable databases, per-edit GitHub PR publisher, watchdog, unsupervised/automatic provider migration.

**Alternative considered / why rejected:** (1) Two permanent user-image authorities (legacy immutable release photos and new R2 photos) require duplicate link resolution and thumbnail handling; (2) retaining immutable release content offline makes new D1 edits and R2 photos stale or unavailable until a software deployment; (3) a full rewrite of the verified service-worker reliability layer risks losing tested atomic-cache safeguards; (4) automatic download/update on every launch adds unnecessary network/storage overhead and violates accepted explicit preparation. Instead retain FISH091 proven integrity primitives while decoupling content generations.

**Acceptance / engineering contract:** [FISH-TODO-118 consolidated acceptance ledger](../../FISH-TODO-118_CONSOLIDATION_SCOPE.md) is a subordinate, stable-ID checklist; [WORK_QUEUE.md](../../WORK_QUEUE.md) alone governs active priority/next safe action. No item is field accepted merely because source CI passes. Before owner field acceptance, demonstrate baseline-ID completeness, D1 revision/CSRF + media consistency, all original image inventory/hash parity, no staged-only R2 read, bounded media handling, independent release/snapshot compatibility, incremental offline preparation retaining the previous good generation under partial/quota/corruption/eviction, Offline no-network/read-only and protected drafts; test Windows Edge and Android installed PWA.

**Authorization boundary:** Owner approved **design, bounded source-only implementation, documentation and CI**. Does **not** by itself approve provider credentials/bindings, R2 writes/migration, D1 schema/data changes, Worker deployment, public routing, application/governance PR merges, or final public V3 cutover. Request each independent consequential approval under [OPERATING_RULES](../../OPERATING_RULES.md).

**Reconsider only if:** Concrete tests/field evidence show D1/R2 offline snapshots cannot retain verified FISH091 safety within reasonable device storage, or a new owner decision changes offline authoring, multi-user/availability or operating model. Any fallback must be explicitly evaluated and approved, never silently recreate dual content authorities.
