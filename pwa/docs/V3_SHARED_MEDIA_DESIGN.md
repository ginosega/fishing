No accepted D5 Notes editor source is modified. Text and link Save remains available.

## Storage choice (recommendation, NOT approved provisioning)

| Option | Fit | Deficiency |
|---|---|---|
| Worker static assets | Preserve original files as immutable backup/archive and keep application UI assets | A permanent second live content-image source would duplicate resolution; new uploads would require redeployment |
| D1 BLOB in existing database | No new binding | Cloudflare D1 **2,000,000-byte row/BLOB limit** conflicts with accepted 10 MiB photos; large binary rows burden the content database and backups |
| **One private R2 for all content images** | **Owner-approved architectural target (ADR-0012)**: migrate V1/V2 originals and store future V3 content photos together, with D1 path ownership and revision checks | Existing private bucket was verified; each R2 binding, historical object write/migration and D1 schema/data change still requires separate owner approval |

## Completed source-only staging vertical (not routed or deployed)

- `pwa/server/d6-shared-media-stage.mjs` exports one private-R2 staging handler with **default OFF**, reuses AUTH-P0 owner session and CSRF `stage-media` authorization, rejects cross-origin, bearer, wrong intent, unsupported formats, unsafe Notes asset paths, oversized streams, magic/content-type/hash mismatches, and invalid dimensions.
- Uses a SHA-256 content-addressed `staged/v1/sha256/<digest>` key and R2 conditional `put` (no overwrite). Verifies returned R2 object metadata or a pre-existing matching object; a staging receipt explicitly says `published:false`. **It does not add a user-visible route or create live media references.**
- Supports the **same Notes image path contract** for Gear, KB and Catches by calling the accepted `noteImagePath`. The accepted 10 MiB upload limit remains. The initial byte validator checks headers/signatures/dimensions; complete decoder parity for animated GIF/WebP and full security regression must be completed before enabling provider writes.
- `pwa/tools/d6-media-schema.mjs` proposes `d6_media_objects` and `d6_media_refs` as a local-file-only SQL generator. **Neither table exists in live D1. Do not run the SQL without a fresh explicit owner approval and D1 backup.**
- Targeted `pwa/test/d6-shared-media-stage.test.mjs` checks all-domain owner paths, default OFF, authorization/CSRF/cross-site denials, immutable idempotent staging, SHA mismatch/MIME/path denial and schema no-destructive-write properties. The private Worker does **not** import, mount or call the staging service.

**Important remaining work before provider activation:** Approve binding/schema separately; complete Gear/KB cover and KB Knot-specific media rules, integrated client Save/preview with dynamically verified image path registry, offline/read-only/draft recovery, expiration/orphan policy and image decoder/animation validation. Keep stage/publish/read routes OFF until those independent implementation and acceptance gates pass.

## Completed source-only D1 publication and linked-media reader prototype

- `pwa/server/d6-shared-media-live.mjs` (ISOLATED / UNMOUNTED / DEFAULT OFF) implements one common `POST /api/v3/media/publish` and `GET|HEAD /api/v3/media/live/<canonical-logical-path>` handler for **Notes Markdown images only** across Gear, KB and Catches. The HTTP adapter reuses existing owner AUTH-P0 cookies and domain-specific CSRF Save intents. No legacy GitHub editor or publisher path is enabled.
- For publishing, the server checks strict image path ownership, actual parsed Markdown `image` tokens (not arbitrary text or link substrings), original R2 staged-object SHA-256 metadata, MIME and size, Ajv record schema, initial revision and Catch linked references. **The staged R2 object never becomes public merely by staging.**
- The **shared** `pwa/server/d6-content-save-transaction.mjs` persistence core now handles all Gear/KB/Catch text Saves (revision-conditional single-record D1 writes) and this disabled media publisher (one transactional `CONTENT_DB.batch` with a SQLite revision guard, record Save/Add, immutable media-object metadata and path mappings). If any statement fails, D1 rolls back the entire batch. Catch Add uses revision 0; Gear/KB edits and Catch edits require the exact current revision. Logical media paths are insert-only (no accidental overwrite). On ambiguity or unexpected response, refuse success and reconcile; do not retry blindly.
- The read-only handler resolves **only D1-listed paths**, verifies the current source row still contains a real Markdown image token for the logical path, checks the matching R2 object's private content-addressed key and metadata, and serves that content with `nosniff` and `no-store`. Staged-only bytes, forged logical paths and removed Notes image links cannot be read. Range requests are currently rejected; streaming/range optimization is a later review item.
- `pwa/test/d6-shared-media-live.test.mjs` uses `node:sqlite` in-memory tables and a fake private R2 binding to test transactional all-or-nothing behavior, a concurrent revision race, immutable path collisions, two-image batch rollback, all three domains, Catch Add, anonymous linked GET/HEAD, owner CSRF/cross-origin denials, staged-only 404 and stale/unlinked Markdown image 404. Unlike UI snapshot tests, the rollback tests run **actual SQLite transactions**; D1 production still requires owner-authorized isolated acceptance.
- This source **does not provide** Gear cover images, KB cover images, KB Knot sequences, new source-image resolver bindings in the existing browser UI, R2 object cleanup, full animated image decoder parity, or final live backend tests. These are necessary before any public-ready shared image upload feature is claimed.

**No Worker imports either isolated media service**, no Wrangler R2 binding exists, SQL generator has never been run on owner D1, and the bucket was empty at the last owner-reported preflight. The shared C04 Save core is source-tested, but the live text-only endpoints are unchanged until a separately approved deployment. Neither source CI nor this prototype is permission to stage or publish live media.

## One shared media service and client (proposed API, not executable)

- `POST /api/v3/media/stage`: same-origin, verified owner session, session-bound CSRF, upload intent, strict content length and method, no bearer-token fallback; accept at most one validated original per request, with batch orchestration for Knot sequences. Revalidate magic bytes, MIME, size, hash and allowable dimensions on the server; never trust client metadata alone. Require image types from the accepted allowlist (no SVG or HTML). Reject duplicates, path traversal and any out-of-scope domain/record.
- Stage immutable, content-addressed R2 objects in a private bucket; no public bucket listing or directly public R2 origin. Names use digest/opaque IDs to prevent overwrite and directory traversal. R2 `put` receipt proves bytes are stored but **does not alone make a content edit live**.
- D1 media metadata (source-only proposal currently uses `d6_media_objects` plus `d6_media_refs`; schema separately approved): logical media path, domain, owner record ID, blob SHA-256, content type, byte count and storage key. **ADR-0012 requires verifying and copying every historical V1/V2 content photograph into private R2 before cutover**. Preserve logical image paths where safe, reconcile SHA-256/size and references, retain original Worker/GitHub copies as archival backup but **not as a permanent alternative online content-image authority**. App UI graphics are independent immutable software assets. New media becomes live only after an owner-authenticated, expected-revision-checked D1 Save publishes the record and R2 metadata atomically; never publish a staged-only image. Failed/stale Save must not produce a live dangling reference. Handle staged orphan cleanup only with an independently approved, bounded retention policy—never delete still-referenced bytes on first replacement.
- `GET /api/v3/media/<validated-logical-path>`: read only a D1-indexed, live media mapping; return R2 bytes with verified MIME, Content-Length, strong immutable ETag, `X-Content-Type-Options: nosniff`, suitable cache and range handling. Read access aligns with the currently anonymous Gear/KB/Catch library; uploading remains owner-only. No arbitrary R2 key access or user-supplied external URL proxy.
- One shared browser uploader and server image handler, with policy-based domain differences only: Gear cover image and Notes, KB cover/Notes/Knot sequence (atomic complete sequence), Catch Notes images. Shared progress/failure/retry receipts, media preview, filename collision policy, and persisted verification. Files over 10 MiB remain rejected unless the product requirement and validator are explicitly revised.
- **Critical integration:** The existing Notes parser/preview, `knownPaths`, static release manifest and `ctx.asset(...)` only resolve frozen image paths. The future client **must** extend the verified path registry to include D1-authorized live media and resolve them via the private Worker GET route. A successful upload without this reader integration is not an accepted feature.
